# 每轮工作流技术复盘

Owner 于 2026-10-18 要求：每轮任务结束都分析工作流是否真正提效，并将数据、结论、修改建议放入私人仓库 `Luok1xi/opus-codex-studio`。这是持续收尾要求；无需逐轮重复请求上传许可。若用户后来收窄范围，以新指令为准。

## 一轮怎样划分

一轮是一个用户目标或明确验收阶段，从接到目标到交付结果。过程中的工具调用、进度提问、子任务和同目标补充，不各自另建复盘；取消、失败或阻塞也留记录。收尾报告、上传和通知不递归触发新复盘。

开始时记任务ID、时间、输入/代码版本、验收条件、分工和预期收益。结束时记测量截止点；结果已完成但上传尚未验证时，不能写“已归档”。本规则依靠实际执行任务的代理读取并遵守，不是已安装的后台监听器，也不能保证未加载规则的其他会话自动执行。

## 固定步骤

1. **交付后核证据**：完成了什么、未完成什么、是否首次通过、返工几次、缺陷是否被发现且修复。没有测量不能填零。
2. **记录开销**：墙钟时间、模型调用/真实用量、工具失败、人工介入、协调等待、重复工作、复核与归档自身开销。原生子代理、真实Opus/DeepSeek调用、仅文件移交分别记录。
3. **判断收益**：先质量后速度。输出“可比样本显示更快/更慢/无变化”“只有局部收益证据”或“证据不足”。不得因为多人并行或交付了很多文件就宣布提效。
4. **提出少量改动**：每项写问题、证据、修改位置、负责人、状态、下一轮如何验证。涉及对方执行且未得到对方回执的建议保持 proposed；自己已实施的规则可记 adopted，但收益验证仍待后续证据。
5. **本地验证并归档**：报告JSON用 `tools/workflow_review.py` 校验并生成易读Markdown；只将本轮报告、脱敏聚合证据和必要工作流改动放入私人仓库。保留其他未提交工作。
6. **验证远端**：再次确认目标仓库仍为private，读取最新分支；提交后核对提交SHA和文件内容/hash。冲突重新读取，不force覆盖。最终给出报告链接和一句结论；失败保留本地待同步状态和原因。

文件约定：`reports/workflow/YYYY-MM-DD-任务短名/{review.json,review.md,evidence.json}`。`evidence.json`可选，具体来源可在JSON内列明。索引为 `reports/workflow/README.md`，建议统一留在 `reports/workflow/IMPROVEMENTS.md`，状态变化保留证据。

```text
python tools/workflow_review.py reports/workflow/2026-10-18-smartcar-research/review.json
python -m unittest discover -s tests -p test_workflow_review.py -v
```

## 数据口径与结论约束

| 数据 | 合法口径 | 不能怎么用 |
|---|---|---|
| 总耗时 | 带时区的开始至测量截止；注明暂停/等待是否包括 | 不能拿工具运行耗时相加当整轮耗时 |
| 并行区间 | 子任务活动区间重叠 | 不等于有效工作时间，更不等于节省时间 |
| token/费用 | 同提供方原始usage、账单；说明缓存与父子范围 | 字符数、工具输出token估算、账户剩余额度不能换算成实付费用 |
| 累计用量 | 同会话连续且同口径的期末减期初 | 计数重置、压缩、分支或重复历史时不得强行做差 |
| 成果与缺陷 | 每项有产物/测试/代码证据，区分发现与修复 | 审稿意见数量不等于已修缺陷数量 |
| 首次通过/返工 | 预先确定同一验收门槛后统计 | 尚未验收不能计入通过分母 |
| 协作成立 | 有真实回复并核验成果，或标记仅文件交接 | “doctor正常”“文件写入”不等于Opus已答复 |
| 基线对照 | 相同任务输入、验收、环境和明确比较协议 | 不同任务快慢不能证明工作流因果收益 |

工具只有在两组均通过同一质量门槛、且任务/验收/环境指纹及比较协议一致时，计算观察到的耗时变化 `(基线秒-本轮秒)/基线秒`。单组或单对结果都不足以宣布普遍因果收益；还需同类任务多次配对并记录顺序、缓存、模型版本等混杂因素。不要为凑对照默认重跑付费模型；优先使用已有合格基线，缺少时记空。

`null`代表未知，`0`代表明确观测到零，两者必须区分。证据路径或hash保证能回查，但hash本身不证明结论成立。人工填写的指标注明来源，校验器不声称自动验证了所有事实或自动脱敏。

## 默认改进策略

- 在分派前读实际入口、当前版本和最新交接；探测一次可用渠道，别反复尝试已知不可用的CLI。
- 每个子任务给唯一范围和简短验收；有价值的第二次独立核查不算无意义重复，但照实计入成本。
- 将源代码事实、作者自述、推测和未验证区分；发现状态冲突先标注再修，不能按文件日期就判断全部内容更新。
- 能用确定性脚本/已有依赖完成的检查，不增加模型委员会。
- 大工具结果只提取必要字段。分析本身也要计算成本；普通轮次尽量一页，小任务一条简报，复杂轮次按证据展开，不追加无效复查。

## 上传边界

授权目的仅为私人工作流分析与改进。上传白名单为上述报告目录、模板、工具/测试及相关工作流规则。不要上传原始聊天/推理、账号/密钥/cookie/授权URL、个人聊天截图、原始会话日志、`.studio-runtime`、未授权项目源码或整目录备份。优先上传聚合指标、必要代码片段/测试结论、公开链接和去除个人路径的证据索引。

GitHub鉴权不可用时先完成本地报告，明确 pending_sync；不索取密码，不为上传开新账户，不公开仓库。用户已授权范围内的正常同步直接完成。
